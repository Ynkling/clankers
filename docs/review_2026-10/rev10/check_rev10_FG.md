## FREQHINGE: what it reads, and the caveat

- **No label reaches the statistic.** `freq_types(tokens)` (`explore_g_s87_child.py`:80-89) is called only from `frequent()` (:102) and the CHECK (:249). `frequent()` calls it on `sample_tokens()`, which is `make_batch(4096, Generator(87000))[0][:, :-1]` (:92-93). `make_batch` returns `(tokens, query streams)`, and the streams are dropped. The term (`term_value`, :107-115) reads the gates, the forward's input token ids and that table. The CHECK's float-tensor refusal does not by itself exclude labels, because stream labels are LongTensors too. The call path does.
- **When it is computed.** Lazily, at the term's first use (training update 1), in each run's process, from a sample that depends only on the generator seed. All 30 FREQ records hold the same table. "Computed once before training" (tex10:283) is right in effect.
- **What it selects.** Token ids are CTX 0-1, KEY 2-5 and VAL 6-21. The 22 input tokens per sequence hold 5 CTX, 9 KEY and 8 VAL, so the frequencies come out analytically as CTX 0.1136, KEY 0.1023 and VAL 0.0227. The records give 0.11368 / 0.11359, 0.10266-0.10165 and 0.02356 at most. The largest ratio, 4.31x, cuts after the six CTX and KEY types.
- **How far it coincides with the key positions.** Completely, plus extras. In every sequence the frequent positions are 14: 5 CTX and 9 KEY. The key term's 8 body-KEY positions are all among them, so 8 of the 14 are the key term's own. The other 6 are the 5 CTX positions, where grouping by token id is grouping by stream, and the query's KEY.
- **The caveat.** On this task the frequency cut is exactly "not a value token". FREQHINGE therefore reads the key term's positions and identities, plus the stream tokens grouped by stream, plus the query's key. Report 7:88-90 and tex10:283 ("happens to select ... covers the key term's eight positions and, beyond them, the query's key and the five context positions") both say so.
